# Дизайн: два генератора карточек с авто-failover (десктоп + ноутбук)

Дата: 2026-06-26. Репозиторий изменений: `agent_convert_foto_rituailb2b2` (VPS API + агент)
плюс донастройка ноутбука. Связанный потребитель очереди — `content-factory` (cards_run).

## Проблема

Контент-карточки генерирует локальный ПК-агент (Playwright→Chrome→ChatGPT-проекты),
который тянет задачи из очереди на VPS. Раньше «контент-машиной» был мощный десктоп,
включённый 24/7. Сейчас из-за перебоев с электричеством десктоп часто выключен и не
запускается удалённо — генерация встаёт. Нужно, чтобы карточки мог генерировать и
ноутбук владельца, **но без конфликтов**: две машины не должны работать одновременно
(один аккаунт ChatGPT, общая очередь).

## Цель и НЕ-цели

**Цель:** ноутбук как второй генератор с **авто-failover** и **приоритетом десктопа**:
- десктоп включён → работает он, ноут в standby;
- десктоп пропал (нет heartbeat > 15 мин) → ноут автоматически перехватывает;
- десктоп вернулся → ноут **дорабатывает текущую карточку** и уступает (грациозный хендбэк);
- обе выключены → никто (нормально).

**НЕ-цели (YAGNI):**
- Разделение каналов/категорий/режимов по машинам — не нужно: единая очередь + один
  активный воркер в каждый момент решает задачу без разделения потоков.
- Параллельная генерация на двух машинах — явно запрещена дизайном.
- Изменения в `content-factory` — не требуются (оно лишь кладёт задачи в ту же очередь).

## Архитектура

Очередь (`/root/ritualb2b/queue.db` на VPS) остаётся единственным источником правды.
Добавляется лёгкий слой «лиз активного воркера с приоритетом».

```
[Десктоп] remote_agent.py  ─┐
  WORKER_ID=desktop, prio=1 │  POST /api/worker/lease (worker_id, priority)
                            ├────────────────► [VPS queue.db]  workers(worker_id,priority,seen_at)
[Ноутбук] remote_agent.py  ─┘  ◄──────────────  ответ: {"active": true|false}
  WORKER_ID=laptop,  prio=2
```

Сервер на каждый `lease` обновляет `seen_at` воркера и вычисляет активного:
**среди воркеров со свежим heartbeat (seen_at в пределах TTL) активен тот, у кого
наименьший priority** (1 = высший). Возвращает вызывающему `active: true|false`.

Агент в начале каждого рабочего цикла вызывает `lease`. Если `active=false` — **не берёт
`/api/next-job`**, спит интервал и повторяет. Если `active=true` — работает как сейчас.

### Таблица результата по состояниям

| Десктоп | Ноут | Активный воркер |
|---|---|---|
| вкл | вкл | десктоп (ноут standby) |
| выкл | вкл | ноут |
| вкл | выкл | десктоп |
| выкл | выкл | никто |

## Изменения по компонентам

Все изменения **аддитивны и обратно-совместимы**: если у агента нет `WORKER_ID` в `.env`,
он считает себя `active=true` (текущее поведение) — десктоп продолжает работать без правок,
пока ему не добавят переменные.

### 1. VPS API (`vps/vps_api.py`) + схема `queue.db`

Новая таблица:
```sql
CREATE TABLE IF NOT EXISTS workers (
  worker_id TEXT PRIMARY KEY,
  priority  INTEGER NOT NULL DEFAULT 100,
  seen_at   TEXT NOT NULL
);
```

Новый эндпоинт:
```
POST /api/worker/lease   (заголовок x-agent-token)
  body/form: worker_id=<str>, priority=<int>
  → upsert workers(worker_id, priority, seen_at=now)
  → active = (нет другого воркера со свежим seen_at и меньшим priority)
  → 200 {"active": true|false, "worker_id": ..., "active_worker": <id|null>}
```
- «Свежий» = `seen_at` в пределах `LEASE_TTL_SECONDS` (по умолчанию **900 с = 15 мин**).
- Тай-брейк: среди свежих воркеров с минимальным priority активен один — с лексикографически
  наименьшим `worker_id` (детерминированно, исключает ситуацию «двое активных» при равном
  приоритете). В штатной конфигурации priority различны (1 и 2), тай-брейк не задействуется.
- Старый `/api/heartbeat` и таблица `agent_heartbeat` остаются без изменений (бот их использует).

### 2. Агент (`remote_agent.py`)

- Читает из `.env`: `WORKER_ID` (str, опц.), `WORKER_PRIORITY` (int, по умолчанию 100),
  `LEASE_POLL_SECONDS` (по умолчанию 15).
- В главном цикле перед `/api/next-job`: вызвать `/api/worker/lease`.
  - `active=false` → лог «standby (активен: <id>)», спать `LEASE_POLL_SECONDS`, не брать задачи.
  - `active=true` → как сейчас (взять задачу, генерировать, complete/fail).
- Грациозный хендбэк получается сам: лиз гейтит только взятие *новой* задачи; задача,
  уже находящаяся в обработке, доводится до конца независимо от смены active.
- Если `WORKER_ID` пуст → лиз не вызывается, `active=true` (обратная совместимость).

### 3. Ноутбук (эта машина) — донастройка

1. **SSH-туннель к :8765.** Проверить, авторизован ли существующий `~/.ssh/id_ritualb2b_claude`
   на VPS для проброса порта; если нет — создать ключ ноутбука и добавить в `authorized_keys`
   на VPS с тем же ограничением `restrict,permitopen="127.0.0.1:8765",command="/bin/false"`.
   Прописать путь в `.env` → `VPS_SSH_KEY`, `VPS_HOST=213.109.202.45`, `VPS_SSH_USER=root`.
2. **`.env`:** `WORKER_ID=laptop`, `WORKER_PRIORITY=2`.
3. **Chrome+ChatGPT:** убедиться, что Chrome запускается `start_chrome.bat` (CDP :9333) и
   `chrome_profile` залогинен в нужный аккаунт ChatGPT с доступом к проектам (профиль 5 ГБ —
   вероятно уже залогинен; проверить открытием проекта).
4. **Зависимости:** `pip install -r requirements.txt` + `playwright install chromium`
   (или системный Chrome через CDP).
5. **WatchDog в Task Scheduler** (как на десктопе): держит агента живым, пока ноут включён;
   сам агент гейтится лизом (работает только когда active). Имя задачи отличное от
   десктопного, чтобы не путать.

### 4. Десктоп — одна правка

В `.env` десктопа добавить `WORKER_ID=desktop`, `WORKER_PRIORITY=1`. До этого десктоп
работает по дефолту (active=true), т.е. порядок выкатки безопасен: сначала VPS+ноут, десктоп
подключаем к схеме последним.

## Тайминги

- `LEASE_POLL_SECONDS = 15` (как текущий цикл поллинга).
- `LEASE_TTL_SECONDS = 900` (15 мин): десктоп считается ушедшим только после 15 мин тишины —
  переживает перезагрузку ПК, кратковременное отключение света/сети, не «дёргает» передачу.

## Риски и откат

- **Прод-система** (генерит и для ритуального бизнеса владельца). Снижение: изменения
  VPS-API аддитивные; лиз-гейт включается только при наличии `WORKER_ID`; десктоп без правок
  работает как раньше; выкатка поэтапная (VPS → ноут → десктоп-env).
- **Один аккаунт ChatGPT.** Failover гарантирует, что в каждый момент ходит одна машина.
- **Деплой VPS** — админ-ключом `id_ritualb2b_admin`, с бэкапом `queue.db` (`cp queue.db
  queue.db.bak-<дата>`) и `py_compile` перед `systemctl restart ritualb2b-api`.
- **Откат:** удалить эндпоинт/не слать lease (агент без `WORKER_ID` → active=true). Таблица
  `workers` безвредна.

## Тестирование (TDD, где применимо)

- **VPS API (юнит):** lease выбирает активного по приоритету; устаревший (seen_at > TTL)
  воркер игнорируется; равный/одинаковый id → активен сам; неизвестный токен → 403.
- **Агент (юнит):** при `active=false` не вызывает next-job; при `active=true` берёт; при
  пустом `WORKER_ID` лиз не вызывается (active=true). Мокать HTTP (как в существующих тестах).
- **E2E (ручной, на проде с подтверждением):** оба воркера онлайн → генерит только десктоп;
  гасим десктоп → через ≤15 мин ноут перехватывает; поднимаем десктоп → ноут доводит текущую
  и уходит в standby. Проверять по логам агентов и `workers.seen_at`.

## Порядок реализации (для плана)

1. VPS API: таблица `workers` + `/api/worker/lease` + тесты. Деплой на VPS (бэкап БД).
2. `remote_agent.py`: лиз-гейт + env + тесты.
3. Ноут: SSH-ключ/туннель, `.env` (laptop/prio2), Chrome/ChatGPT проверка, deps, WatchDog.
4. Десктоп `.env`: desktop/prio1 (последним).
5. E2E-проверка failover и хендбэка.
